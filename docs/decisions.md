# Design decisions

Code comments and the spike notes refer to these decisions by their IDs: E1 to E24 for the control layer (E1 to E13 from the first version), P1 to P20 for the PowerPoint converter.

| ID | Decision | Choice | Reason |
|---|---|---|---|
| E1 | Input formats | Keynote HTML export and claude.ai decks; PowerPoint and Google Slides go through PPTX, then Keynote. **Revised by P1:** PowerPoint files are read directly | current PowerPoint versions have no HTML export |
| E2 | Google Slides | PPTX download, opened and exported in Keynote. **Revised by P1:** the PPTX download goes to deckfold directly | Google Slides exports no HTML; no adapter of its own needed |
| E3 | Target browsers (revised by E14) | the same presenting in every browser; Chrome and Edge add Keyboard Lock (Escape in full screen comes as a key; since E24 one Escape ends the presentation in every browser) | no browser reports reliably which screen a window is on, so deckfold does not check it in any browser (E14) |
| E4 | Where the presenter view is configured | defaults from CLI flags or a JSON file, changeable at runtime and stored per deck in the browser | fixed starting point, adjustable on site |
| E5 | Presenter view elements (revised by E20) | current slide and next step, notes, time, slide overview; shown or hidden, notes size, target duration and pane sizes are changed while the view runs | matches Keynote and PowerPoint, plus an overview for jumping |
| E6 | Notes for Keynote decks | none | the Keynote HTML export contains no presenter notes |
| E7 | Auto mode timing | timings from the source first, otherwise a global interval; waits for playing media; optional loop | keeps the intent of the source and never cuts off a video |
| E8 | Media size | embedded unchanged, decoded on demand, warning above a threshold. **Revised by E17:** pictures and fonts are converted. **Revised by E18:** video and sound that browsers do not play everywhere are converted when ffmpeg is installed | no quality loss, no dependency on a transcoder |
| E9 | Live web content | stays live; offline it shows the still image of the source or a placeholder; reported during conversion | keeps interactivity and still works offline |
| E10 | Asset cannot be resolved | abort with a list of locations; `--lenient` writes the file anyway | the default output is guaranteed to be self-contained |
| E11 | Extent of the clean-up | safe changes only; CSS and JS content stays unchanged | animations must not break |
| E12 | Code signing | binaries are unsigned; the README describes how to allow them | no cost, can be added later |
| E13 | Unknown format | abort; `--generic` embeds it without presenter view, overview and auto mode | the presenter view never goes missing silently |
| E14 | Presenting (v0.4.0) | the window the file is opened in is the presentation, with a start screen (preview, slide strip, settings); the presenter view is a second window the user switches on and drags to a screen; deckfold places no window and does not check where the windows are, so full screen can always be chosen; the previews show whole slides after all their steps (in the presenter view since E20 the state on screen and the state of the next click); the source player runs only after "Start", and the end reloads the window back to the start screen; one Escape ends the presentation (Keyboard Lock in Chrome and Edge) | without the window management permission Chrome puts every popup on the opener's screen, Safari and Firefox never place windows. Without the permission no browser reports reliably which screen a window is on (Wayland reports no positions; macOS with separate Spaces shows a dragged window on the screen under the mouse, while browsers report the screen with the larger part of it). A draft of v0.4.0 asked for the permission in Chrome and Edge and blocked full screen while both windows were on the same screen; in the maintainer's test this did not work reliably, so it was removed and placing the windows is left to the user, see `docs/spikes/S2-file-protocol.md` |
| E15 | Input and the player's state (v0.4.0, swipes revised by E22) | a click on the slide is "next" through deckfold; the wheel and swipes are taken before the source player and dropped (since E22 deckfold reads a swipe on a touch screen itself); after every move and once a second the show window compares the slide the player shows with its own state and jumps back when they differ (at most twice for the same state); a preview reaches each state within one task, so no step in between is painted | the claude.ai player moves by itself on a click, on the wheel and on a swipe, the Keynote player on a swipe; a player that moved past deckfold left the presentation and the presenter view on different slides, and back no longer reached the first slide. Previews pressed the steps one after another, and every step was painted |
| E16 | What is written on the slides (v0.5.0) | every output of a claude.ai, Keynote or PowerPoint deck holds a content model next to the deck metadata: for each slide its text blocks with a role, the step in which each shows where the source tells it (PowerPoint and claude.ai; the Keynote export does not, so its blocks have none), and links to other slides; a title only where the source marks one (the title placeholder of PowerPoint, the label of claude.ai; Keynote marks none), and no role is guessed from size or position. A search and an outline on the start screen and in the presenter view use it, in one overlay; the notes are searched only in the presenter view, and choosing an entry goes to the start of its slide like a slide tile does. A link to another slide goes through deckfold's state. `--content` writes the model as JSON or Markdown; `--refresh` adds it to older claude.ai and Keynote outputs. The source players stay, and the source HTML is not changed for it | until then deckfold knew how a slide runs (steps, timings, notes) and not what is on it. The source players stay because they are what keeps the slides looking like the original. A guessed title would be wrong on some slides without anyone noticing, so a slide without a marked title shows its number and the start of its text. The start screen may already be on the projector, which is why it does not show notes. A link the player followed by itself would leave the presentation and the presenter view on different slides (see E15) |
| E17 | Pictures and fonts (after v0.6.0) | while converting, every picture and font the page shows goes into a format that browsers support widely and that is smaller: PNG, GIF (also animated), BMP and TIFF become lossless WebP, TrueType, OpenType and WOFF fonts become WOFF2. A converted file replaces the original only when it is smaller and reading it back with another decoder gives the same picture, every sample of it, or the same font tables; a TIFF is converted whenever deckfold can read it, because only Safari shows TIFF. What the target cannot hold, or a browser would show differently, stays as it is: PNG with 16 bits per channel, animated PNG, a PNG whose colours depend on a gamma chunk alone, a PNG with half-transparent pixels (Chrome shows them one level of 255 off in WebP), a turned picture, a GIF with frames under 20 ms or a finite loop count above one run. Colour profiles and EXIF data travel into the WebP file. JPEG, SVG, video and sound are not touched. Files that a script of the source loads itself (the shim table) and icons stay unchanged. `--keep-assets` and the configuration key `keepAssets` switch it off; `--refresh` converts nothing. What the picture encoder wrote is kept in the folder `.deckfold-cache` beside the output (since v0.8.0; `--no-cache`, key `cache`), under a key of the encoder version, its settings and the samples that went in. An entry is the bare output of the encoder and goes the way of a fresh result: deckfold adds profile and EXIF data from the source itself and compares every sample, so a foreign entry is never shown | the files get smaller without a visible change, and TIFF pictures show in every browser; the encoders are part of the binary, so nothing has to be installed. Measurements and the cases that stay: `docs/spikes/S8-media-conversion.md` |
| E18 | Video and sound (v0.9.0) | converted with the ffmpeg that is installed on the machine (`ffmpeg` and `ffprobe` on the PATH), and only what browsers do not play everywhere. HEVC, AV1, WMV, MPEG-2 and H.264 with 10 bits or 4:2:2 become H.264 (High profile, 8 bits, 4:2:0, `-crf 18 -preset veryslow`) in MP4, with every frame, the frame times and the colour tags of the source; H.264 in another container is packed into MP4 with its packets untouched. PCM in a WAV file becomes FLAC when that is smaller and decodes to the same samples; ADPCM in WAV, AIFF and ALAC always become FLAC; WMA and the like become MP3, or AAC for more than two channels. Video with HDR, transparency or interlacing stays, with a warning. Without ffmpeg, or without the encoder a file needs, the file stays as it is and the report says so. Nothing of this is kept in the cache. A file reaches ffmpeg only when deckfold has told its container from the first bytes; the format is always given, the protocols are limited to `file`, and a run without progress is stopped. `--keep-assets` switches it off, and `DECKFOLD_NO_FFMPEG=1` ignores an installed ffmpeg | an ffmpeg inside the binary (WebAssembly, one core, no assembler) needs 7 s for a frame of 1080p video and 18 s for a frame of 4096 x 2160, about 19 hours for the three HEVC videos of a local collection, and with x264 inside deckfold would have to change to the GPL. The installed one is fast, and deckfold ships no encoder and stays under the MIT licence. The price: the output for such files depends on the machine. Measurements: `docs/spikes/S9-video-and-sound.md` |
| E19 | Screen wake lock (after v0.9.0) | the presentation window holds a screen wake lock while the show runs: asked for in the click or key on "Start", before full screen, and again on every key, click and command while none is held, when the page becomes visible, when the browser releases it and every 10 s after a refusal; the presenter view shows "Screen saver not blocked" in its status line while the presentation holds none; the presenter view holds no lock of its own, and there is no stand-in such as a silent looping video | Safari 27.2 grants the lock only shortly after a click or key and refuses it right after `requestFullscreen()` in the same click; Chrome 158 keeps it for a covered presentation window and drops it for a minimized one; with the lock held, the screen saver of macOS did not start (Chrome). What a lock does on Windows, Linux and in Firefox is not measured, and no web page can stop a lock that a policy enforces, so the presenter is told when the lock is missing instead of being promised it; see `docs/spikes/S10-wake-lock.md` |
| E20 | Presenter view layout (after v0.9.1, names and status bar since v0.11.0) | three panes. "Live", large on the left, shows what the audience sees, and before the start the start slide at its first step. "Preview" on the right shows the state the next click leads to: the next step of the slide, or the next slide at its first step. A pane and its switch have the same name, which does not change with what the next click does, and the pane is not marked. The notes stand below it. The heading of "Live" has a dot for each state the slide rests in, filled up to the one shown, and an arrow for the change to the next slide, in the accent colour when the next click makes it; from 13 states on a bar stands for the dots. The top bar has no counter; the status bar shows the number of slides at its left. The overview leaves out the slides hidden from the show (E21). Time and the slide overview are always shown, so only the three panes have switches; the divider above the overview sets the width of its tiles (`presenter.layout.strip`, 96 to 480 px, the overview at most 45 % of the window height). Search and end show are buttons with an icon and the name as tooltip (full screen was one too until E23). Element lists of earlier versions are still read: "current" becomes "audience", "time" and "overview" are dropped, and the share of the removed pane in the layout is ignored | the maintainer chose the arrangement of PowerPoint's presenter view. Until v0.9.1 the large pane showed the current slide after all its steps and "Next" the next slide after all its steps, while the next click often showed a step of the current slide; the audience pane, smaller, repeated the large one at the last step. The dots tell how many clicks are left on the slide without a number to read. In v0.10.0 the right pane was called "Next step" or "Next slide" by what the next click did, its switch "Next click", and it was framed in the accent colour before a change of slide; in use the maintainer found the changing names and the colour confusing and chose fixed names, "Live" and "Preview" as at a video mixer. The counters in the top bar repeated the overview and the dots |
| E21 | Hiding slides from the show (v0.12.0) | every tile on the start screen has an eye at the right of its number that hides the slide from the show or shows it again. "Next", "back", Home, End, the links to the next and previous slide and auto mode skip a hidden slide; a jump to it by its number, a hit of the search or a link to it shows it, and the show goes on with the next shown slide. The show begins on a shown slide: a chosen start slide that is hidden gives way to the next shown one (or the last shown one before it), and the line beside "Start" says so. The last shown slide cannot be hidden. The list is stored per deck in the browser; without one, the slides PowerPoint hides are hidden. The presenter view's overview leaves hidden slides out and follows a change at once, and the count reads "7 of 9 slides". Past a hidden slide PowerPoint's player plays the transition into the next shown slide; the other players jump. No eye where deckfold does not move the player: the generic format and self-playing Keynote exports. `--drop-hidden` (configuration key `dropHidden`) leaves the slides PowerPoint hides out of the file, as before | the maintainer asked for a switch per slide on the start screen; PowerPoint's "Hide Slide" works the same way, and jumps to a hidden slide stay possible there too. A slide hidden in PowerPoint was left out of the file until v0.11.0, so it could not be shown when a question came up; now its text, pictures and notes are in the file, and a file to pass on without such slides needs the option. A jump over a slide with the player's own "next" key would show the hidden slide until the check of E15 brought the player back |
| E22 | Touch in the presentation | deckfold reads a swipe on a touch screen itself and sends it through its own state: to the left is "next", to the right "back", in steps like the arrow keys. A swipe is one finger that begins on the slide and moves at least 48 CSS pixels along one axis, at least twice as far as across it, within 800 ms; it counts when the finger lifts. It is always on and has no setting. A tap stays "next", like a click. The mouse, the wheel and a swipe on a trackpad are as before. A swipe up, or the key of the new action `strip` (G by default), shows a strip of slide tiles at the bottom of the presentation with "End show" beside it; a tile goes to the start of its slide. A slide hidden from the show is greyed out there and can be chosen (E21). A swipe down, a tap or click beside the strip, Escape and the key close it; while it is open, the keys of "next" and "back" move its mark, Enter goes there, and taps and swipes move no slide, while commands of the presenter view still do. The key does nothing in the presenter view. Nothing of this needs full screen or the presenter view. The generic format has neither swipes nor the strip. A default key of `strip` that a configuration or an older file gave to another action stays with that action | the maintainer wants to present on tablets and, later, in an Android app made for it on touch displays, where there is no keyboard: until now a touch could only move on, and neither back, a jump nor the end was within reach. The reason of E15 holds, since the source player still never sees the gesture. The strip is small because the audience sees it. The thresholds are usual values and not measured on a device, and nothing depends on the edge of the screen, which belongs to the system on an iPad. The tiles of the strip are copies of the slides from the document before activation (the snapshot), not from the window's document, which the player has changed by then; a copy does not keep the class the slides are found by. Tested with touches made through CDP in Chrome. By the maintainer on an iPad with Safari (2026-11-25, the file served over the local network, since the Files app shows an HTML file only as a preview): full screen works and hides the address bar, portrait and landscape work, and every swipe down leaves full screen, wherever it begins. What follows from that for full screen is E23. Swipes and the strip on an iPad, a touch display and a WebView are not measured |
| E23 | Full screen and the presenter view by device | on a computer the presenter view is a setting and full screen is one too, on by default, as before. On a phone or tablet (iOS, iPadOS, Android; told from the user agent, an iPad from calling itself a Mac with more than one touch point) the show always runs in full screen and has no presenter view: the start screen shows neither setting, and what the browser stored for them does not count. "Click for full screen" shows only on a computer and only while a request got no full screen. Full screen that was there and is left during the show stays off on a computer (the key of "fullscreen" brings it back; since E24 this holds only for full screen left with that key or under Keyboard Lock, otherwise the presentation ends); on a phone or tablet the next tap or swipe on the slide asks for it again and moves on as usual, except a swipe down. The slide strip has no button for full screen. The presenter view has no full screen of its own on any device: no button, and the key of "fullscreen" does nothing there | the maintainer's rule. A tablet or a touch display shows one window to the audience: a second window opens as a tab there, and nobody leaves full screen on purpose. On an iPad every swipe down leaves full screen (measured by the maintainer, 2026-11-25), and the overlay then came back each time in front of the audience; on a computer it also showed after full screen was left with Escape in Safari and Firefox, where it was no fallback either. A swipe down does not ask again, because it is the gesture that leaves full screen. Whether Safari on an iPad grants full screen from a tap or a swipe that is not a click on a button is not measured; a refused request changes nothing. Tested with a user agent of each kind in Chrome. The presenter view lost its full screen on the maintainer's word: it is the window on the presenter's own screen, and its full screen was where Chrome on a Mac ended full screen at the first click after a drag to another screen (`docs/spikes/S2-file-protocol.md`), a fault no page can work around |
| E24 | One Escape ends the presentation (2026-11-26) | one Escape in the presentation leads back to the start screen, with and without full screen, in every browser. Without full screen the key reaches deckfold, as before. In full screen with Keyboard Lock (Chrome, Edge) it does too. A browser without Keyboard Lock takes the Escape itself and leaves full screen, and there the presentation ends when full screen that was there is gone, unless the key of "fullscreen" left it: then the show goes on in the window, as in E23. So in Safari every other way out of full screen ends the presentation as well, Safari's own button included, and Escape while the slide strip is open ends the show there instead of closing the strip. A show in auto mode that loses full screen there stays on the start screen. With Keyboard Lock, full screen left by holding Escape goes on in the window. A phone or tablet stays as in E23. "Click for full screen" still shows only for a request that got no full screen | the maintainer's rule: Escape means "end", and a second Escape in Safari was a step nobody expects. Measured in Safari 27.2 on macOS 27.2 with real key presses sent through System Events (`docs/spikes/S2-file-protocol.md`): the page gets no `keydown` of that Escape, `fullscreenchange` came in 20 of 20 runs, and a `keyup` of the Escape came in 15 of them, about 0.6 s before full screen was gone; why it stayed away in 5 is not known, so the rule does not use it. Another app in front and Mission Control did not end full screen, and neither did a click into the presenter view while the show was in full screen (by the maintainer, by hand). Not measured: a key pressed by a finger, which is held longer than a key from System Events; Safari's own button for leaving full screen; a video in its own full screen; Firefox with a real key (not installed on the maintainer's Mac; the rule is the same there, tested with a stand-in for full screen); an iPad with a keyboard |

## PowerPoint converter

| ID | Decision | Choice | Reason |
|---|---|---|---|
| P1 | Scope | PowerPoint files (.pptx, .ppsx, .pptm) are converted directly; deckfold renders the slides and plays them with its own player; the control layer stays the same | a PPTX file has no player of its own, and the Keynote route needs a Mac with Keynote and loses the notes |
| P2 | Approach | native Go: slides as SVG, a timing model for animations; the Keynote route stays possible | the only way that needs no installation, keeps the MIT license and runs on all platforms |
| P3 | Scope of the first version (revised by P9) | static content plus the animation core; 3D transitions and Morph are played as a fade | covers most real decks |
| P4 | Text layout | deckfold lays out text itself with the font metrics | text is the largest risk for fidelity, and the result is the same in every browser |
| P5 | Fonts | cascade: fonts embedded in the presentation, then installed fonts, then the bundled OFL fonts; fsType is honoured; subsets are embedded | line breaks match, font licenses are respected |
| P6 | Charts | own SVG drawing for the common chart types, from the data cache in the file | chart slides stay presentable |
| P7 | EMF and WMF | own converter for the common records | logos and older pictures stay visible |
| P8 | Test decks | generated public feature decks with PowerPoint reference images, compared by SSIM | fidelity can be measured and regressions show up |
| P9 | Scope after the first release | every known gap of the converter is closed, also features no real deck used so far | decks from other sources use them |
| P10 | Order | features by how often they occur in real decks: embedded fonts, GIFs, triggers, 3D, picture bullets, effects; then the rest | the most visible gains first |
| P11 | Morph and 3D transitions | objects are paired by "!!" names, otherwise by kind and text, and interpolated in position, size, rotation, color and opacity; geometric 3D transitions with CSS 3D | visible motion without morphing outlines |
| P12 | 3D shape effects | drawn with WebGL (three.js) from the shape's outline | close to PowerPoint |
| P13 | Without WebGL | an SVG approximation (lighting filter for bevels, offset copy for extrusions) is the base drawing; previews keep it | the overview and machines without WebGL stay usable |
| P14 | Tile transitions | WebGL, with the slides drawn into textures; a fade without WebGL | the same graphics basis as P12 |
| P15 | PowerPoint references | made in one announced run per group of decks | few rounds of access dialogs for the maintainer |
| P16 | Keynote and claude.ai decks for the tests | Keynote exports stay local (they contain Apple's player); a neutral claude.ai deck comes from the maintainer | no third-party player code in the repository |
| P17 | WebGL library | three.js, bundled into a classic script with only the parts the player uses, embedded only in decks that need it | a proven library; decks without 3D stay small |

Defaults that were set without a separate decision:

- For Keynote and claude.ai, the source player stays unchanged and deckfold adds a control layer with one adapter per format, because the animations could not be rebuilt faithfully. PowerPoint files have no source player; there deckfold's own player runs under the same control layer (P1).
- PowerPoint: `.ppt` and password-protected files are refused with a hint (exit code 2); hidden slides are skipped; SmartArt is drawn from the drawing PowerPoint stores with it, otherwise a placeholder; equations, ink, OLE objects and 3D models show the fallback picture stored in the file; shadows and glow become SVG filters, 3D bevels are left out and reported; media stays unchanged (E8), WMV, AVI and ASF show only their still image; animations by word or letter are played by paragraph; triggers (interactive sequences) are not played; `advTm` is the source timing for auto mode (E7).
- deckfold is written in Go: one static binary per platform.
- Assets are embedded as Base64 blocks and turned into blob URLs at runtime; fonts load through rewritten `@font-face` rules, and the start waits for `document.fonts.ready`. One-shot assets (scripts, XHR, fetch, worker code) are released after use; assets referenced by the DOM stay.
- Remote resources (for example Google Fonts) are downloaded during conversion.
- The CSP of the source is extended for `blob:` and live embeds.
- Default key bindings follow common presentation clickers and can be changed in the configuration.
- A start screen with a click, because full screen and window placement need a user gesture.
- Audio plays only in the audience window.
- The notes panel is hidden when a deck has no notes (follows from E6).
- The UI language follows the browser language (German or English).
- The output is `<name>.standalone.html` or the `-o` path; the warning threshold is 250 MB.
| P18 | Text blocks and links to other slides | the renderer collects the text of a slide while it draws it: the paragraphs of the slide's own shapes, table cells and SmartArt shapes, with the role from the placeholder type and the bullet, and the description of pictures; not the text of layout and master, the placeholders for date, footer and slide number, or chart labels. The step of a block comes from the animations: the latest first appearance of its paragraph, its shape and the groups around it. A link to another slide (`ppaction://hlinksldjump`, `ppaction://hlinkshowjump`) is drawn with `data-df-jump` on the text or the shape and followed by the control layer; a link to a slide PowerPoint hides leads there (E21), and with `--drop-hidden`, which leaves that slide out, it stays text and is reported | the renderer already knows every paragraph, its placeholder and its bullet, so the content model costs no second pass over the file. Layout and master text would repeat on every slide. Until now such links were drawn as text without an action |
| P19 | Kerning | as PowerPoint does it, measured against its PDF export: a run is kerned when its font size, as drawn, is at least the value of its `kern` attribute (hundredths of a point; no attribute and `0` mean no kerning), with the pairs of the font's legacy `kern` table, also across runs and with the space; GPOS is not read. A bundled font that stands in for another family kerns only where it has the pairs of the original: Liberation Sans for Arial and for upright Helvetica, Liberation Serif for Times New Roman (their `kern` tables), Carlito for Calibri (its GPOS; Carlito Bold kerns 51 pairs more than Calibri Bold and is used all the same). Carlito named by the deck itself is not kerned. Every kerned pair is written as a shift of its own in the SVG, and the slide switches the browser's kerning off; shaped and right-to-left text keeps the kerning of the shaper and the browser. `--refresh` does not draw slides again: an output from before keeps its unkerned lines until the presentation is converted again | lines were up to 0.7 % longer than PowerPoint's, up to 11 % for single words, and broke in other places. The rule is one for all fonts (17 measured), so nothing is tuned per font. A browser kerns with GPOS where PowerPoint takes the `kern` table, and the embedded subsets carry neither, so the positions are deckfold's own; Chrome did kern fonts that are embedded whole, which deckfold measured without kerning |
| P20 | Baselines | as PowerPoint places them, measured against its PDF export: a single line is 1.2 times the font size; the font divides it by the ascender and the descender of its `hhea` table, and the part below the baseline stays the same under every line spacing. The line spacing (percent, points, or a stored reduction) is the distance from baseline to baseline. The baseline lies at least three quarters of that distance below the top of its line and otherwise leaves the font its part below. The text ends below its last baseline by the font's part, which is what centering and bottom alignment use. Every baseline is a whole number of points below the top of the text | the ascent alone put Liberation Sans 2 px and Liberation Serif 3 px too high and Carlito 1 px too low, and a line spacing of 150 % several pixels off. One formula fits 132 baselines in 44 combinations of line spacing, anchor and font and 57 combinations of font and size. Whether the whole points are PowerPoint's layout or its PDF export is not known; they are what the reference images show |
