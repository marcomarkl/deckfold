Ninth pre-release of deckfold: the second conversion of a deck takes seconds, and three things v0.7.0 listed as not tested have been tested.

## Why

Since v0.7.0 deckfold converts pictures to lossless WebP with the slowest and best setting of the encoder. Nine decks of a local collection take 618 seconds that way, and they took them again at every conversion.

## What changed

- **deckfold keeps what the picture encoder wrote.** The folder `.deckfold-cache` beside the output file holds the output of the encoder for every picture. The next conversion takes it from there, and its report says how many encoder runs that saved. The nine decks take 8.9 seconds the second time. Without `-o` the output, and so the folder, is beside the presentation.
- **The output is the same.** With an empty folder, a filled one and with `--no-cache`, deckfold writes the same bytes.
- **An entry of the folder is checked before it is used.** It has to be a plain file as the encoder writes one. deckfold adds the colour profile and the EXIF data of the presentation itself, reads the result with a second decoder and compares every sample with the picture of the presentation. A damaged entry, one of another picture or one that somebody else prepared is not used and gets replaced.
- **`--no-cache` switches the folder off,** and so does `"cache": false` in the configuration file. `--keep-assets` makes no folder. When the folder cannot be written, the conversion goes on without it and the report says so.
- **The first conversion is as slow as before.** The measurement showed where the time goes: only into the encoder, which works on one picture with one core. The pictures were already converted on all cores, and nothing was encoded twice. A deck with one large picture takes as long as that picture, 40 to 115 seconds in the collection.

## What this does not cover

- The folder holds pictures of the slides. Leave it out when you pass the output on. It can be deleted at any time, and deckfold sets no limit to its size.
- Fonts are not kept; they convert in a fraction of a second.
- Video and sound are embedded unchanged, as before.
- Checking an entry shows that it holds the same picture, not that it holds the very bytes the encoder would write. The output is byte for byte the one without the folder when deckfold wrote the entries itself.

## What is tested

- The cache, in unit tests: the same bytes without a folder, with an empty and with a filled one, for a still picture, one with a colour profile and an animation. An entry replaced by damaged data, by another picture, by a file with a foreign colour profile, by an oversized file or by an animation with other frame durations is refused and replaced. The key changes with the encoder version, its settings and the samples.
- The command: the folder beside the output, also with `-o`; the switches and the configuration key, which is not written into the output; a folder that cannot be made; the public decks `media` and `gifs` with a folder whose entries somebody else filled.
- Nine decks of a local collection: 618 s without the folder, 480 s with one empty folder for all nine (they share pictures), 8.9 s the second time. Every output of the second run is the one of the first, and for four decks also the one with `--no-cache`.
- **An animated GIF against its WebP file at short frames,** which v0.7.0 had compared at 500 ms only: frames of 500, 200, 100, 50 and 20 ms keep in step. The test takes screenshots that show both pictures at the same moment and counts how many frames one is ahead of the other. In Chrome and WebKit on a Mac and in Firefox and Chrome on Linux every pair kept its distance in every screenshot but for 1 % at 20 ms in WebKit; in Chrome on Windows in all but 4 % at 500 ms. Pictures of different speeds, as a control, were found at every distance.
- **The fix for the previews of v0.7.0 in Firefox,** which had run there once per CI run: the test for links to other slides passed 200 repeats in Firefox on Linux and the new test for the previews 50. A workflow that is started by hand, `repeat.yml`, repeats a test there.
- **The checksums of the binaries.** The binaries of v0.7.0 built on a Mac and the published ones have the same sizes and other checksums. `go version -m` shows the only difference: the commit and the time that Go writes into a binary.
- In Chrome and WebKit on a Mac: the 146 browser tests. Their setup converts with `--no-cache`, so they see what the encoder made in that run.
- The six binaries build with `scripts/release.sh` on a Mac (19.2 MB to 21.0 MB), and the smoke test passes with the one for macOS (arm64).
- The CI: `go vet`, the Go suite and the smoke test on Linux, Windows and macOS (x64 and arm64), and the browser tests with the public decks in Chrome on Linux and Windows and in Firefox on Linux.

## Not tested yet

- An HTML export with pictures to convert from a real source. The claude.ai deck and the Keynote export of the local collection have none; the tests use a small deck made for it.
- Safari itself, and the rows of `docs/manual-test.md`.
- GIF animations with frames under 20 ms. They are not converted.
