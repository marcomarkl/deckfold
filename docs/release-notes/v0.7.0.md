Eighth pre-release of deckfold: pictures and fonts are converted to smaller formats that show the same.

## Why

deckfold embedded every picture and font as it found it. PowerPoint decks are full of PNG pictures, and deckfold wrote its font subsets as TrueType files. Both have smaller forms that every current browser reads. TIFF pictures went into the file as TIFF, which only Safari shows.

## What changed

- **PNG, GIF, BMP and TIFF pictures become lossless WebP.** Every sample of the picture is kept, the colour of fully transparent pixels included. A colour profile and EXIF data travel into the WebP file. An animated GIF becomes an animated WebP picture and still starts again when its slide is entered.
- **Fonts become WOFF2.** This holds for the font subsets of a PowerPoint deck and for TrueType, OpenType and WOFF fonts of an HTML export. No table of the font is transformed, so a reader gets every table back byte for byte.
- **A converted file replaces the original only when it is smaller and reads back the same.** deckfold reads every result with a decoder that is not the encoder and compares: pictures sample by sample, animations state by state with their durations, fonts table by table. Whatever fails stays as it was, without an error.
- **Some pictures stay as they are,** because the target cannot hold them or a browser would show them differently: PNG with 16 bits per channel, animated PNG, a PNG with half-transparent pixels (Chrome shows such pixels of a WebP file one level of 255 off), a PNG whose colours depend on a gamma chunk alone, a turned picture, and a GIF with frames shorter than 20 ms or with a loop count other than "forever" or "once".
- **TIFF pictures show in every browser,** as far as deckfold can read them. A TIFF in CMYK, with 16 bits per channel, or in a variant the decoder does not read stays TIFF, and the report says so.
- **In an HTML export, only what the page shows is converted:** pictures and fonts from attributes and style sheets. Files that a script of the source loads itself, icons, frames and plugin files are embedded unchanged. Where the type of a file changes, the `type` of its `<source>` element and the `format()` hint of a font follow.
- **`--keep-assets` embeds everything unchanged,** and so does `"keepAssets": true` in the configuration file. The output is then byte for byte the one of v0.6.0.
- **The report says what was converted:** the number of pictures and fonts and their size before and after.
- **Converting takes longer.** deckfold uses the slowest and best setting of the WebP encoder. Nine decks of a local collection that took a few seconds together now take 638 seconds.

## What this does not cover

- JPEG pictures, SVG, video and sound are embedded unchanged. A smaller JPEG would mean encoding again, which changes pixels.
- `--refresh` converts nothing. Convert the presentation again to get the smaller files.
- Pictures that are stored inside an SVG file of the source.
- Building from source needs the build tag `nodynamic` (see the README). A binary built without it leaves pictures unchanged when it finds a libwebp on the machine, and says so.

## What is tested

- The conversion itself, in unit tests: PNG in RGB, with alpha, with a palette and in grey; colour profile, gamma chunk, EXIF data and orientation; animated PNG; still and animated GIF with every kind of frame disposal, checked a second time with the animation decoder of libwebp; BMP; TIFF and its eight orientations; TrueType and WOFF fonts; damaged and oversized data. Fixed inputs give fixed bytes.
- `--keep-assets` against v0.6.0: the 24 public feature decks and nine decks of a local collection give the same bytes.
- Two Keynote exports and a claude.ai deck of a local collection give the same bytes as with v0.6.0, with and without the switch: their pictures are loaded by the player of the source or are JPEG, and their fonts are WOFF2 already.
- Nine decks of a local collection: 235 pictures and 42 fonts were converted, 177.0 MB became 93.6 MB. The nine output files went from 980.1 MB to 869.1 MB.
- In Chrome and WebKit on a Mac: the 143 browser tests, among them the image comparison with PowerPoint for every feature deck at unchanged thresholds, that the WebP pictures decode and the WOFF2 fonts load, and that an animated WebP picture starts again when its slide is entered.
- What the browsers show, by screenshot in Chrome and WebKit: a PNG with a Display P3 profile, without colour data, with sRGB and gamma chunk, with EXIF data and with a pixel density, each against its WebP file. The comparison was shown to fail for a WebP file without the profile. WebKit shows every pair the same; Chrome differs only in half-transparent pixels, which is why such PNG pictures are not converted.
- An animated GIF and its WebP file side by side in Chrome and WebKit: frames of 500 ms change at the same moments, and a GIF that plays once stops on the same frame.
- The binaries for the six platforms build without CGO with the flags of `scripts/release.sh`; the smoke test passes on macOS (arm64).

## Not tested yet

- Firefox, and Chrome on Linux and Windows: these run in the CI, which has not run for this change. The test with the fixed bytes will show there whether the results are the same on every platform.
- `scripts/release.sh` itself, and the sizes of the binaries it builds.
- An HTML export with pictures to convert from a real source. The claude.ai deck and the Keynote export at hand have none; the test uses a small deck made for it.
- Safari itself, and the rows of `docs/manual-test.md`.
- GIF animations with frames shorter than 500 ms against their WebP files.
